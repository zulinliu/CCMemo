# Phase 0.4.1 Plan: 安全与设置骨架

**Version:** v0.4.0  
**Phase:** 0.4.1  
**Status:** Planned, not implemented  
**Depends on:** v0.4.0 design confirmation  
**Primary files likely touched during implementation:** Rust server/auth/config/service modules, frontend settings shell, README  
**Non-goal for this planning step:** Do not implement code while writing this plan.

## 1. Goal

建立 v0.4.0 的安全和设置基础，使 CCMemo 的本地访问模型、认证模型、Host/CORS 行为、Settings 数据来源与文档承诺一致。

用户运行 `ccmemo serve` 后，应明确知道：服务只在本机监听、如何登录、数据路径在哪里、当前版本和安全状态是什么。

## 2. User Story

**作为** 注重隐私的 Claude Code 高频用户，  
**我希望** CCMemo 默认只允许本机访问，并在设置页清晰展示数据路径和安全状态，  
**以便** 我能放心把本地 Claude Code transcript 交给 CCMemo 索引和浏览。

## 3. Scope

### In scope

- 统一认证主路径决策。
- 默认监听地址从公网风险行为收敛到本机访问。
- Host 与 CORS 默认安全策略。
- 去除固定默认密码风险。
- Settings API 只读骨架。
- Settings UI 只读入口。
- README / CLI 输出与真实行为对齐。
- 安全相关测试计划。

### Out of scope

- Web scan 入口。
- Search parser。
- Resume check。
- Export/redaction。
- SQLCipher。
- OS Keychain。
- Tauri 桌面化。
- 多用户账户。

## 4. Locked Decisions

1. v0.4.0 继续 Web 单机交付，不引入 Tauri。
2. Settings v0.4.0 默认读多写少，本阶段只要求只读可用。
3. 默认不开放局域网访问。
4. 不再允许固定默认密码作为生产行为。
5. 若开发模式需要放宽 Host/CORS，必须通过显式 flag 或环境变量启用。

## 5. Open Decisions to Resolve Before Coding

| Decision | Recommended choice | Reason |
|---|---|---|
| 认证主路径 | HttpOnly cookie session | 当前前端已按 cookie 工作，改动最小，适合浏览器 UI |
| API token 是否保留 | 作为可选机器访问模式，不作为 Web 主路径 | 避免 README 与实现冲突，同时给 CLI/API 用户留扩展 |
| localhost 是否默认允许 | 允许 `127.0.0.1`，`localhost` 可允许但需匹配实际端口 | 符合用户直觉，仍防 DNS rebinding |
| Settings 是否可写 | v0.4.1 只读 | 降低配置生效、重启、校验复杂度 |

## 6. Proposed Backend Design

### 6.1 Config additions

Add explicit config fields conceptually equivalent to:

```rust
struct ServerConfig {
    bind_host: IpAddr,
    port: Option<u16>,
    auth_mode: AuthMode,
    allow_lan: bool,
    dev_relaxed_security: bool,
}
```

Implementation may keep the existing `Config` struct and gradually refactor, but behavior must be explicit.

### 6.2 Auth behavior

Recommended model:

- Browser login uses password/access-code and receives HttpOnly cookie.
- Cookie contains random session ID only.
- Server stores active session IDs in memory for v0.4.1.
- If no password is configured, `ccmemo serve` generates a one-time access code and prints it once.
- Fixed fallback `123456` must be removed.

### 6.3 Host validation

Default allow list:

```text
127.0.0.1:<actual-port>
localhost:<actual-port> optional if resolved as local use case
```

Explicit unsafe/LAN mode:

```text
ccmemo serve --host 0.0.0.0
```

When enabled, CLI output must show a warning.

### 6.4 CORS

Default:

- Allow only same-origin and local dev origin when explicitly in dev.
- Do not use `Any` in production path.

### 6.5 Settings API

```text
GET /api/settings
```

Suggested response:

```ts
interface SettingsSnapshot {
  version: string
  claude_config_dir: string
  db_path: string
  export_dir: string
  bind_address: string
  auth_mode: 'cookie_session' | 'token' | 'access_code'
  lan_exposed: boolean
  dev_relaxed_security: boolean
  last_scan_at: string | null
  stats: {
    session_count: number
    project_count: number
    event_count: number
    tool_call_count: number
  }
}
```

## 7. Proposed Frontend Design

### 7.1 Settings entry

Add a header entry or lightweight settings panel route/modal. Prefer a panel over a full routing refactor in this phase.

### 7.2 Settings sections

- 数据位置
  - Claude config dir
  - Database path
  - Export dir
- 安全状态
  - 当前监听地址
  - 是否仅本机可访问
  - 当前认证方式
- 索引状态
  - 上次扫描时间
  - 会话、项目、事件、工具调用数量
- 版本与帮助
  - CCMemo version
  - README/help link or copyable CLI help command

### 7.3 Copy and interaction

- Long paths must be copyable.
- If a field is read-only, do not show editable controls.
- If a setting requires restart in future, label it as “当前版本只读”。

## 8. Tasks for Future Implementation

1. Refactor `server::start_server` default bind host to local-only.
2. Remove fixed default password fallback.
3. Add one-time access code behavior or require configured password.
4. Normalize auth documentation and login copy.
5. Replace permissive CORS defaults.
6. Tighten Host validation by actual port.
7. Add `GET /api/settings` handler.
8. Add frontend Settings panel.
9. Update README quick start and security section.
10. Add tests for unauthenticated API access and default bind behavior.

## 9. Acceptance Criteria

- `ccmemo serve` defaults to a local-only URL.
- No fixed default password is accepted unless user explicitly configured it.
- CLI output explains how to access the UI and whether LAN exposure is enabled.
- Unauthenticated calls to business APIs return no session/project/stat data.
- `GET /api/settings` returns paths, version, bind/security state and stats for authenticated users.
- Settings UI displays paths and security state without editable controls.
- README matches actual auth and bind behavior.

## 10. Test Plan

### Backend tests

- Default bind host is local-only.
- Unsafe/LAN mode requires explicit opt-in.
- Missing auth cannot access `/api/sessions`, `/api/projects`, `/api/stats`, `/api/settings`.
- Login succeeds with generated/configured access credential.
- Host validation rejects spoofed or mismatched hosts.

### Frontend tests

- Settings panel renders path values.
- Long path copy button works or shows fallback error.
- Security status shows local-only vs LAN-exposed.
- Unauthenticated settings access returns to login.

## 11. Risks

| Risk | Mitigation |
|---|---|
| Tight Host/CORS breaks local dev | Add explicit dev relaxed flag, never default it in release |
| Removing default password changes existing user habit | Print generated access code clearly, document env var for persistent password |
| Settings write capability scope creep | v0.4.1 only read-only; defer writes |

## 12. Definition of Done

This phase is done when CCMemo has a trustworthy local-only startup baseline, a consistent authentication story, a readonly Settings surface, and documentation that matches runtime behavior.
