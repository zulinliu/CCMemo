# CCMemo v0.4.0 设计自审报告

**评审对象**：`.planning/v0.4.0/DESIGN.md`  
**评审日期**：2026-06-06  
**评审方式**：多角色模拟评审（产品、研发、测试、UI/UX、运营、法务/合规）  
**结论**：有条件通过

## 1. 总体判定

**结论：有条件通过。**

v0.4.0 方向合理：先补齐本地 Web 使用闭环，而不是继续扩张 AI/Skill 功能。方案覆盖了安全、扫描、搜索、恢复、导出、设置等日常可用能力，符合当前项目阶段。进入开发前，需要进一步细化认证模型、扫描任务并发、完整导出读取策略、数据库迁移和测试用例边界。

## 2. 通过条件与不可上线条件

### 2.1 进入开发的通过条件

满足以下条件，可进入 phase plan 和实现拆分：

1. 明确认证主路径：cookie session 或 API token，避免 README、CLI、前端三套说法不一致。
2. 明确 Web scan 的并发规则：单任务、重复提交、失败恢复、全量重扫确认。
3. 明确 export 的“完整内容”读取策略，不能继续只导出 preview。
4. 明确 search parser 的语法边界和 SQL 参数化策略。
5. 明确 settings v0.4.0 哪些字段只读、哪些字段可写。

### 2.2 不可上线条件

存在以下任一情况，不应发布 v0.4.0：

1. 默认仍监听 `0.0.0.0` 且无强提示。
2. 默认仍使用固定密码 `123456`。
3. `--safe` 导出参数存在但不脱敏。
4. Web 扫描失败会清空或破坏已有索引数据。
5. 未认证请求可以读取 session/project/stats 数据。
6. README 对认证、访问地址、导出安全的描述与真实行为不一致。

## 3. 风险分级

## 3.1 阻断项

| # | 问题 | 提出角色 | 影响 | 修改建议 |
|---|---|---|---|---|
| 1 | 认证模型尚未最终拍板，cookie session 与 token header 存在文档/实现偏差 | 产品、研发、法务 | 安全承诺不可信，用户和 API 使用者困惑 | v0.4.0 开发前写明唯一主路径；如双轨支持，明确使用场景和优先级 |
| 2 | 完整导出策略仍需技术验证，现有数据结构只有 preview，完整内容需依赖 fileOffset/byteLength 回读原始 JSONL | 研发、测试 | 若不解决，Export 无法达到“完整会话记录”目标 | 先实现 raw event reader service，并为文件缺失、offset 失效、UTF-8 边界写测试 |

## 3.2 重要项

| # | 问题 | 提出角色 | 影响 | 修改建议 |
|---|---|---|---|---|
| 1 | ScanStatus 如果只放内存，server 重启后状态丢失 | 研发、测试 | 用户无法追踪最后扫描结果 | v0.4 可内存 + last scan summary 持久化，或 settings 中只展示最后完成时间 |
| 2 | `POST /api/scan` 缺少取消语义 | 产品、测试 | 大量 transcript 时用户可能被长任务卡住 | v0.4 可不做取消，但需明确“扫描可后台进行，不阻塞浏览”；v0.4.1 补取消 |
| 3 | 结构化搜索中 `project:` 是匹配项目名还是 project_id 未定义 | 产品、研发、测试 | 用户输入不符合预期，测试不可写 | 推荐 project: 先匹配项目名和路径片段，精确 project_id 作为内部参数 |
| 4 | 安全导出的误伤防护较复杂，容易导致漏脱敏 | 法务、测试 | 分享导出仍可能泄露敏感数据 | v0.4 以“宁可多脱敏”为原则；fake/test 仅降级显示 warning，不阻断替换 |
| 5 | Settings 可写能力若做半截，容易造成配置修改不生效 | 产品、UI/UX | 用户误以为已保存 | v0.4 Settings 建议只读为主，可写项延期，所有需重启项明确标注 |
| 6 | Host/CORS 需要兼顾本地、dev server、tunnel 调试，容易破坏开发体验 | 研发 | 开发调试不便或生产安全过宽 | 增加显式 dev flag，不把 tunnel 作为默认允许项 |

## 3.3 建议项

| # | 问题 | 提出角色 | 建议 |
|---|---|---|---|
| 1 | Command Palette 可提升开发者效率，但会扩大范围 | 产品、UI/UX | v0.4 先保留 Ctrl/Cmd+K 聚焦搜索，完整命令面板延期 |
| 2 | 书签/页边注很符合品牌，但不是落地闭环必需 | 产品、UI/UX | 只做设计预留，不在 UI 主入口展示未实现功能 |
| 3 | after/before 搜索有价值，但涉及日期解析和时区边界 | 测试、研发 | v0.4.1 再做，v0.4 只在 parser 结构中预留 |
| 4 | AI/Skill 入口禁用态可能让用户失望 | 产品、运营 | 文案强调“先导出完整会话”，不要展示不可点击假功能 |

## 4. 各角色评审意见

## 4.1 产品经理视角

**判定：通过。**

优点：

- 版本主题聚焦，符合当前“可浏览但不闭环”的阶段。
- P0/P1/P2 边界清晰，避免 AI 和 Skill Forge 过早吞噬工期。
- 主流程完整：启动、认证、扫描、搜索、查看、恢复、导出、设置。

风险：

- 成功指标还偏定性，开发前可补充更明确的数值，例如首次扫描、搜索响应、导出耗时。
- Command Palette、书签、页边注需要严格延期，否则容易范围蔓延。

产品建议：

- v0.4.0 版本口径应固定为“实用化闭环”，不要在发布文案中主打 AI 或 Skill。
- Release notes 中明确 AI/Skill 是后续方向，避免用户期待错位。

## 4.2 研发工程师视角

**判定：有条件通过。**

技术可行性总体成立，但有几个实现前必须收口的点：

1. **认证模型**：当前 cookie session 和 token header 的差异必须统一，否则前后端和 README 都会反复返工。
2. **完整导出**：现有事件 preview 不能满足完整导出，需要 raw reader。若 transcript 文件不存在，必须有降级策略。
3. **扫描任务**：需要单任务锁和状态存储，避免重复扫描并发写 SQLite。
4. **search parser**：必须后端参数化，不允许把用户查询拼 SQL。
5. **数据库迁移**：任何新增表或字段都需要 migration version。

粗略工作量：

- 后端：8-12 人日
- 前端：6-9 人日
- 测试与文档：4-6 人日
- 合计：18-27 人日，适合拆 4 个小阶段完成。

## 4.3 测试工程师视角

**判定：有条件通过。**

测试重点：

- 安全：默认 bind、未认证 API、错误响应不泄露。
- 扫描：无数据、少量数据、大量数据、损坏 JSONL、重复扫描、扫描失败。
- 搜索：普通文本、中文、IME、结构化 filter、特殊字符、SQL 注入样例。
- Resume：路径存在/不存在、Claude CLI 存在/不存在、shell unknown。
- Export：原始导出、安全导出、文件缺失、offset 失效、敏感样例。

需要补充的边界：

- 单个 transcript 超大时的导出超时策略。
- 导出文件名冲突策略。
- Windows 路径、中文路径、空格路径。
- 用户快速切换会话时 resume/export 请求竞态。

## 4.4 UI/UX 设计师视角

**判定：通过。**

优点：

- 延续“纸感 + 现代工具”的产品 UI，不引入多余装饰。
- FirstRunEmptyState、ResumeCard、ExportCard、SettingsPanel 都是当前体验缺口。
- 把 AI/Skill 入口做禁用态或弱提示，避免虚假可用。

注意事项：

- 扫描和导出不要只用 spinner，应展示阶段、数量和结果。
- 安全导出是高信任场景，文案要具体，不要写“已保护您的隐私”这种空泛话。
- Settings 中的路径较长，需要支持复制和横向截断。
- 移动端报告页新增卡片后，要避免底部 tab 下内容被遮挡。

## 4.5 运营/增长视角

**判定：通过。**

虽然 CCMemo 是本地单用户工具，不需要传统埋点，但仍需要“自诊断数据”：

- indexed session count
- last scan time
- scan errors count
- export count 可以不上传，只在本地展示或日志中保留

发布建议：

- v0.4.0 文案主打“无需离开 Web 完成扫描、恢复和导出”。
- README Quick Start 要更新为 Web-first 流程。
- Demo 数据仍是冷启动关键，应保留“导入示例会话”。

## 4.6 法务/合规视角

**判定：有条件通过。**

主要关注：

- Transcript 可能包含 API key、私人路径、邮箱、客户信息、源码片段。
- 安全导出不能承诺 100% 脱敏，只能说明“按规则检测并替换常见敏感信息”。
- 原始导出必须明确警示。
- 默认不联网的承诺必须真实。AI/Skill 未来接外部 Provider 时，需要发送前预览和用户确认。

合规建议：

- 在 Settings 或 Help 中加入“数据只存储在本机”的说明。
- 对 safe export 使用“规则脱敏”而不是“安全分享无风险”的措辞。
- 导出水印不应包含用户路径或敏感信息。

## 5. 修订后设计约束

基于自审，v0.4.0 开发前应固化以下约束：

1. 认证模型先统一，后写代码。
2. 导出必须从 raw transcript 读取完整内容，preview 只作为降级。
3. Web scan 只能单任务运行。
4. Settings v0.4.0 默认只读。
5. Safe export 默认宁可多脱敏，不为了减少误伤而冒泄露风险。
6. AI/Skill 入口不主推，不制造“马上可用”的错觉。

## 6. 最终评审结论

v0.4.0 设计可以进入下一步规划拆分。推荐下一步不是直接实现，而是创建 4 个 phase plan：

1. 0.4.1 安全与设置骨架
2. 0.4.2 扫描与搜索闭环
3. 0.4.3 Resume 与 Export 闭环
4. 0.4.4 质量收口与发布文档

每个 phase plan 都应包含可执行验收标准和测试计划。
